## A. 모델 선택 및 아키텍처

### Q1. 왜 Qwen2.5-72B를 베이스 모델로 선택했나요?

**답변:**

베이스 모델을 고를 때 우리가 가장 중요하게 본 것은 3가지입니다:

1. **다국어 지원**: 우리 시스템은 한국어, 일본어, 영어를 모두 다뤄야 합니다. Qwen2.5는 중국 Alibaba에서 만든 모델인데, 학습할 때 동아시아 언어(중국어, 일본어, 한국어)를 많이 포함시켜서 이 3가지 언어를 잘 이해합니다. 반면 Llama 같은 모델은 영어 위주라서 한국어/일본어 성능이 떨어집니다.

2. **모델 크기(72B)**: 우리에겐 A100 40GB GPU가 8장 있습니다. 72B 모델을 4비트로 양자화하면 GPU 4장(약 36GB × 4 = 144GB 중 실제 약 38GB/장)에 올릴 수 있습니다. 더 큰 모델(예: 405B)은 GPU가 부족하고, 더 작은 모델(7B, 14B)은 복잡한 기술 문서를 이해하는 능력이 부족합니다.

3. **오픈소스 라이선스**: Qwen2.5는 Apache 2.0 라이선스로, 상용 환경에서도 자유롭게 사용할 수 있습니다.

**비교표:**

| 모델 | 크기 | 다국어 | GPU 요구량 (4bit) | 라이선스 |
|------|------|--------|------------------|---------|
| Llama 3.1 70B | 70B | 영어 중심 | GPU 4장 | Llama License |
| Qwen2.5 72B | 72B | 동아시아어 강점 | GPU 4장 | Apache 2.0 |
| Mistral Large | 123B | 유럽어 중심 | GPU 6장+ | 제한적 |

→ 결론: **GPU 4장으로 올릴 수 있는 최대 크기 + 다국어 최강 = Qwen2.5-72B**

### Q2. Qwen2.5-72B의 모델 아키텍처 구조를 설명해주세요.

**답변:**

쉽게 설명하면, 이 모델은 "글을 읽고 다음 단어를 예측하는 기계"입니다. 구조를 단계별로 풀어볼게요:

```
입력: "tjesmgr BOOT 명령어는"
    ↓
[토크나이저] - 글자를 숫자로 변환 (152,064개의 단어 사전 사용)
    ↓
[임베딩 레이어] - 숫자를 의미 벡터로 변환 (8192차원)
    ↓
[트랜스포머 블록 × 80층] - 핵심 두뇌 (여기가 제일 중요!)
    │
    │  각 층에는:
    │  ├─ Self-Attention (64개 헤드, KV 8개 헤드) - "어떤 단어가 중요한지 집중"
    │  ├─ FFN (Feed-Forward Network, 29568차원) - "정보를 변환"
    │  └─ RMSNorm - "값이 너무 크거나 작아지지 않게 조절"
    │
    ↓
[출력 레이어] - 다음에 올 단어 확률 계산
    ↓
출력: "TJES 시스템을 부팅하는..."
```

**핵심 숫자:**

| 항목 | 값 | 쉬운 설명 |
|------|-----|----------|
| 파라미터 수 | 73.5B (735억개) | 뇌의 시냅스 연결 수와 비슷 |
| 트랜스포머 레이어 | 80층 | 80겹으로 쌓인 "생각하는 층" |
| Hidden Size | 8,192 | 각 단어를 8192개의 숫자로 표현 |
| Attention Heads | 64 (KV: 8) | 64명이 동시에 다른 관점에서 분석 |
| FFN 크기 | 29,568 | 중간 변환 통로의 넓이 |
| 단어 사전 | 152,064개 | 알고 있는 단어/토큰의 수 |
| 최대 입력 길이 | 32,768 토큰 | 한 번에 읽을 수 있는 최대 글자 수 |
| 활성화 함수 | SiLU (Swish) | "중요한 정보만 통과시키는 필터" |

**GQA (Grouped Query Attention) 설명:**

보통 Attention은 Query 64개, Key 64개, Value 64개가 1:1로 짝을 이루지만, Qwen2.5는 Key/Value를 8개만 사용합니다 (64:8 비율). 이것을 GQA라고 합니다.

왜 이렇게 하냐면, Key와 Value를 저장하는 "KV Cache"가 추론할 때 GPU 메모리를 많이 차지하기 때문입니다. 8개로 줄이면 메모리를 8배 절약하면서도 성능 저하는 거의 없습니다. 비유하자면, "기자(Query) 64명이 편집자(KV) 8명에게 질문하는" 구조로, 편집자 수를 줄여 사무실(GPU 메모리)을 절약하는 것입니다.

### Q3. 왜 72B 모델을 선택했나요? 7B나 14B로는 안 되나요?

**답변:**

처음에는 7B 모델(Qwen2.5-7B)로 시작했습니다. 하지만 실제 테스트에서 큰 문제가 발생했습니다:

**7B 모델의 한계:**
- OpenFrame 기술 문서에는 "tjesmgr", "DSALC_ERR_DATASET_NOT_FOUND" 같은 전문 용어가 많습니다
- 7B 모델은 이런 전문 용어를 학습해도 **다른 제품 정보와 섞어버리는 현상(할루시네이션)**이 심했습니다
- 예: "tjesmgr에 대해 설명해줘"라고 물었는데 oscmgr(다른 제품) 정보가 섞여 나옴

**72B 모델의 장점:**
- 파라미터가 10배 많으니, 각 제품의 지식을 **서로 다른 뉴런에 저장**할 수 있습니다
- 비유하자면: 7B는 작은 방에 22개 제품의 책을 다 쌓아놓은 것, 72B는 큰 도서관에 제품별 서가를 따로 만든 것

**실험 결과 비교:**

| 항목 | 7B | 72B |
|------|-----|------|
| 할루시네이션 비율 | ~47% | ~15% |
| 제품 간 교차 오염 | 심함 | 낮음 |
| 에러코드 정확도 | ~60% | ~85% |
| GPU 필요량 | 1장 | 4장 |
| 추론 속도 | ~30 tok/s | ~6 tok/s |

→ 속도는 5배 느리지만, **정확도가 훨씬 중요한** 기술 문서 QA 시스템에서는 72B가 필수적이었습니다.

### Q4. 모델의 최대 컨텍스트 길이를 4096으로 제한한 이유는?

**답변:**

Qwen2.5-72B 모델은 원래 **32,768 토큰**까지 지원합니다. 하지만 우리는 **4,096 토큰**으로 제한했습니다. 이유를 단계별로 설명하면:

**1. GPU 메모리 제약**

Attention 연산의 메모리 사용량은 시퀀스 길이의 **제곱**에 비례합니다:
```
4096 토큰: 메모리 1배 (기준)
8192 토큰: 메모리 4배
16384 토큰: 메모리 16배
32768 토큰: 메모리 64배
```

A100 40GB GPU 4장에서 72B 모델(4bit 양자화)을 올리면 이미 약 38GB/장을 사용합니다. KV Cache를 위한 여유 공간이 약 2GB/장뿐이라 긴 시퀀스는 불가능합니다.

**2. RAG 시스템에서는 4096이면 충분**

우리 시스템의 동작 방식:
```
사용자 질문 (약 100 토큰)
+ 검색된 문서 조각 3~5개 (각 500~800 토큰 = 약 2500 토큰)
+ 시스템 프롬프트 (약 500 토큰)
= 총 약 3100 토큰 (입력)
+ 응답 생성 (약 800 토큰)
= 총 약 3900 토큰
```

→ RAG는 전체 문서를 넣는 게 아니라, **관련 조각만 검색해서 넣기 때문에** 4096이면 충분합니다.

**3. 동시 처리 능력 (Concurrency)**

```
4096 토큰 × 63.7 동시 요청 = 약 26만 토큰의 KV Cache
```

컨텍스트를 줄이면 동시에 처리할 수 있는 요청 수가 늘어납니다. 현재 설정으로 **약 63개 요청을 동시 처리** 가능합니다.

### Q5. Tensor Parallel Size 4를 사용한 이유는?

**답변:**

72B 모델은 하나의 GPU에 다 올라가지 않습니다. 그래서 **모델을 4조각으로 나눠서 GPU 4장에 분산**합니다. 이것을 "텐서 병렬화(Tensor Parallelism)"라고 합니다.

**동작 원리를 쉽게 설명하면:**

```
[GPU 4] 모델의 1/4   ←→   [GPU 5] 모델의 2/4
    ↕                          ↕
[GPU 6] 모델의 3/4   ←→   [GPU 7] 모델의 4/4
```

비유: 4명이 긴 책을 각자 1/4씩 담당해서 동시에 읽는 것과 같습니다. 각 층(80개)의 Attention Head 64개를 16개씩 GPU 4장에 나눕니다.

**왜 Pipeline Parallel이 아닌 Tensor Parallel인가?**

| 방식 | 설명 | 장점 | 단점 |
|------|------|------|------|
| Tensor Parallel (TP) | 각 층을 가로로 분할 | 지연시간(Latency) 낮음 | GPU 간 통신 많음 |
| Pipeline Parallel (PP) | 층을 세로로 분할 (1~20층 → GPU1, 21~40층 → GPU2...) | 통신 적음 | 지연시간 높음 (Bubble) |

우리는 **실시간 채팅 서비스**이므로 응답 지연이 적은 TP를 선택했습니다. A100은 NVLink로 연결되어 GPU 간 통신 속도가 빨라서 TP의 단점(통신 오버헤드)이 크지 않습니다.

## B. 학습 파이프라인 (CPT → SFT → DPO)

### Q6. 전체 학습 파이프라인을 설명해주세요. 왜 3단계로 나눠서 학습했나요?

**답변:**

우리의 학습은 3단계로 이루어져 있습니다. 이것을 사람의 교육에 비유하면 이해하기 쉽습니다:

```
[1단계: CPT]     대학생이 전공 교과서를 통독하는 것
     ↓           "OpenFrame이라는 분야가 있구나, 용어가 이렇구나"
[2단계: SFT]     실무 인턴십에서 선배의 Q&A를 보며 배우는 것
     ↓           "이런 질문에는 이렇게 대답하는구나"
[3단계: DPO]     상사의 피드백으로 좋은 답변과 나쁜 답변을 구분하는 것
                 "이 답변은 O, 저 답변은 X"
```

**각 단계의 목적:**

| 단계 | 정식 명칭 | 목적 | 비유 |
|------|----------|------|------|
| CPT | Continued Pre-Training | 도메인 지식(전문 용어) 학습 | 교과서 읽기 |
| SFT | Supervised Fine-Tuning | 질문-답변 형식 학습 | 모범 답안 공부 |
| DPO | Direct Preference Optimization | 할루시네이션 억제 | 오답노트 학습 |

**왜 한 번에 안 하고 3단계로 나누나?**

한 번에 모든 것을 학습시키면 **학습 목표가 충돌**합니다:
- CPT: "다음 단어를 예측해!" (자유로운 생성)
- SFT: "이 형식대로 답변해!" (구조화된 응답)
- DPO: "이건 좋은 답, 이건 나쁜 답!" (선호도 학습)

비유하면, 동시에 "자유롭게 써!", "형식 맞춰!", "틀린 것 피해!" 라고 하면 혼란스럽지만, 순서대로 가르치면 체계적으로 배울 수 있습니다.

### Q7. CPT (Continued Pre-Training)는 구체적으로 무엇을 하는 건가요?

**답변:**

CPT는 "도메인 지식 주입"입니다. Qwen2.5-72B는 인터넷의 일반 텍스트로 학습된 모델이라 "tjesmgr", "DSALC_ERR_DATASET_NOT_FOUND" 같은 **OpenFrame 전문 용어를 모릅니다**. CPT에서는 이 전문 용어를 모델에 가르칩니다.

**학습 방식: 다음 단어 예측 (Next Token Prediction)**

```
입력:  "tjesmgr BOOT 명령어는 TJES 노드를 [???]"
정답:  "초기화"
모델:  "시작" → 틀림 → 가중치 업데이트
       "초기화" → 맞음 → 가중치 유지
```

모델은 OpenFrame 매뉴얼을 계속 읽으면서 "이 용어 다음에는 이런 말이 온다"를 학습합니다.

**CPT 학습 데이터:**

| 항목 | 값 |
|------|-----|
| 일본어 매뉴얼 텍스트 | 807,119줄 (30.2MB) |
| 한국어 매뉴얼 텍스트 | 100,208줄 (4.3MB) |
| 혼합 코퍼스 총량 | 907,326줄 (34.5MB) |
| 학습 청크 수 | 4,009개 (학습) + 211개 (검증) |
| 원본 소스 | 19개 OpenFrame 제품 PDF 매뉴얼 |

**일본어가 한국어보다 8배 많은 이유:**
- OpenFrame 고객의 대부분이 일본 금융기관
- 일본어 매뉴얼이 가장 상세하고 양이 많음
- 한국어 매뉴얼은 상대적으로 간략

**CPT 학습 결과:**

| 지표 | 값 | 의미 |
|------|-----|------|
| 학습 손실(Train Loss) | 0.1141 | 모델이 도메인 텍스트를 잘 학습함 |
| 검증 손실(Eval Loss) | 0.5022 | 약간의 과적합이 있지만 수용 가능 |
| Perplexity | 1.6524 | 1에 가까울수록 좋음 (도메인 적응 성공) |
| 학습 가능 파라미터 | 842M (전체의 1.14%) | LoRA로 효율적 학습 |

### Q8. SFT (Supervised Fine-Tuning)에서 왜 제품별로 따로 학습했나요?

**답변:**

SFT에서는 **22개 OpenFrame 제품에 대해 각각 별도의 LoRA 어댑터**를 만들었습니다. 하나로 합치지 않은 이유가 있습니다:

**제품별 분리의 이유:**

1. **할루시네이션 방지**: 하나의 모델에 22개 제품을 다 넣으면, "TJES의 명령어를 알려줘" 했을 때 OSC의 명령어가 섞여 나옵니다. 제품별로 분리하면 각 어댑터가 **자기 제품만 알고** 있어서 교차 오염이 줄어듭니다.

2. **데이터 불균형 대응**: 제품별 학습 데이터 양이 매우 다릅니다:
   ```
   JEUS:           980개 (가장 많음)
   Tibero:         231개
   OpenFrame OSI:  192개
   OpenFrame Base: 250개
   ProSync:         72개 (가장 적음)
   ```
   하나로 합치면 JEUS가 대부분을 차지해서 다른 제품은 잘 학습되지 않습니다.

3. **독립적 업데이트**: 특정 제품의 매뉴얼이 업데이트되면 그 제품의 어댑터만 다시 학습하면 됩니다. 전체를 재학습할 필요가 없습니다.

**실제 학습된 10개 SFT 어댑터 (현재 서빙 중):**

| 어댑터명 | 제품 | 학습 데이터 | 학습 손실 | 검증 손실 | 학습 시간 |
|----------|------|-----------|----------|----------|----------|
| openframe_base | Base 서비스 | 250개 | 0.5109 | 0.4647 | 20분 |
| openframe_batch | 배치 처리 | ~200개 | ~0.55 | ~0.50 | 18분 |
| openframe_common | 공통 모듈 | ~200개 | ~0.53 | ~0.48 | 17분 |
| openframe_hidb | 계층형 DB | ~180개 | ~0.58 | ~0.52 | 16분 |
| openframe_osc | 온라인 트랜잭션 | ~190개 | ~0.56 | ~0.50 | 17분 |
| openframe_osi | OSI 모듈 | 192개 | 0.6464 | 0.5383 | 15분 |
| openframe_tacf | 보안 모듈 | ~180개 | ~0.57 | ~0.51 | 16분 |
| openframe_vos3 | VOS3 지원 | ~170개 | ~0.59 | ~0.53 | 15분 |

| openframe_gateway | 게이트웨이 | ~160개 | ~0.60 | ~0.54 | 14분 |

### Q9. DPO (Direct Preference Optimization)는 왜 필요했나요? SFT만으로는 부족한가요?

**답변:**

SFT만으로는 "좋은 답변을 배우는 것"만 가능합니다. **"나쁜 답변을 피하는 것"은 배우지 못합니다**. 이것이 DPO가 필요한 핵심 이유입니다.

**비유로 설명:**
```
SFT  = 모범 답안만 보고 공부 → "이렇게 쓰면 되는구나"
DPO  = 채점된 답안지를 비교 → "이건 O, 이건 X, 차이는 이거구나"
```

**구체적인 문제:**

SFT 후에도 E2E 테스트에서 **할루시네이션 비율이 47%**였습니다:
```
질문: "tjesmgr BOOT에 대해 설명해주세요"
SFT 답변: "tjesmgr BOOT는 TJES를 초기화합니다. oscmgr와 함께 사용되며..."
                                                    ↑
                                              이 부분이 할루시네이션!
                                              (oscmgr는 다른 제품)
```

**DPO의 학습 방식:**

DPO는 "좋은 답변(Chosen)"과 "나쁜 답변(Rejected)"을 쌍으로 보여주고, 좋은 답변에 높은 점수를 주도록 학습합니다:

```json
{
  "prompt": "tjesmgr BOOT 명령어를 설명해주세요",
  "chosen": "tjesmgr BOOT는 TJES 노드를 초기화하는 명령어입니다. [출처: TJES 가이드]",
  "rejected": "tjesmgr BOOT는 TJES와 OSC를 함께 초기화하는 통합 명령어입니다..."
}
```

**DPO 학습 데이터 생성 전략 (4가지):**

| 전략 | 비율 | 설명 | 예시 |
|------|------|------|------|
| factual_product_swap | 55.7% | 다른 제품의 답변을 rejected로 사용 | TJES 질문에 OSC 답변을 rejected |
| factual_desc_swap | 34.4% | 사실이 틀린 설명을 rejected로 사용 | 버전 번호, 기능 설명 오류 |
| sft_cross_match | 9.4% | SFT 모델의 실제 오답을 rejected로 사용 | 실제 테스트에서 틀린 응답 |
| e2e_cross_product | 0.6% | E2E 테스트 실패 케이스 활용 | 실제 할루시네이션 사례 |

### Q10. DPO의 Beta 값이 0.1인데, 이 값의 의미는 무엇인가요?

**답변:**

Beta(β)는 DPO에서 가장 중요한 하이퍼파라미터입니다. **"원래 모델에서 얼마나 멀리 떨어져도 되는지"를 정하는 값**입니다.

**쉬운 비유:**
```
β = 0.01 (너무 작음): "선생님 말씀은 무시하고 학생 마음대로 해!"
                      → 보상 해킹(Reward Hacking) 위험
β = 1.0  (너무 큼):   "선생님 말씀만 100% 따라! 새로운 건 배우지 마!"
                      → 학습 효과 없음
β = 0.1  (적당):      "새로운 것도 배우되, 원래 알던 것도 잊지 마!"
                      → 균형잡힌 학습
```

**기술적 설명:**

DPO의 손실 함수는:
```
Loss = -log σ(β × (log π(chosen) - log π(rejected) - log πref(chosen) + log πref(rejected)))
```

여기서 β가 하는 역할:
- β가 클수록: 원래 모델(πref)과 비슷하게 유지하려는 힘(KL Divergence 패널티)이 강해짐
- β가 작을수록: 선호도(chosen/rejected) 차이를 크게 벌리려는 힘이 강해짐

**우리의 실험:**

| Beta | 결과 |
|------|------|
| 0.05 | 제품별 DPO에서 사용. 데이터가 적어서(~100쌍) 조심스럽게 학습 |
| 0.1 | 통합 DPO에서 사용. 데이터가 많아서(1800쌍) 좀 더 공격적으로 학습 |
| 0.3 | 테스트했으나 학습이 거의 되지 않음 (KL 패널티가 너무 강함) |

### Q11. CPT, SFT, DPO 각 단계의 Learning Rate가 다른 이유는?

**답변:**

각 단계마다 학습률(LR)이 다릅니다. 이유를 비유로 설명하면:

```
CPT: LR = 1e-5 (0.00001)  → 교과서를 천천히 읽기 (지식 주입)
SFT: LR = 1e-4 (0.0001)   → 문제집을 빠르게 풀기 (패턴 학습)
DPO: LR = 5e-6 (0.000005) → 오답노트를 아주 조심히 검토 (미세 조정)
```

**각 LR 선택 이유:**

| 단계 | LR | 이유 |
|------|-----|------|
| CPT (1e-5) | 중간 | 새로운 도메인 지식을 배워야 하지만, 기존 언어 능력을 잃으면 안 됨. 너무 크면 "Catastrophic Forgetting"(기존 지식 망각) 발생 |
| SFT (1e-4) | 큼 | Q&A 형식은 기존 지식과 충돌하지 않으므로 빠르게 학습해도 안전. 명확한 입출력 패턴이 있어서 수렴이 빠름 |
| DPO (5e-6) | 매우 작음 | 이미 CPT+SFT로 잘 학습된 모델을 "살짝만" 조정하는 것. 너무 크면 기존에 잘 답변하던 것도 망가짐 |

**실제 발생한 문제:**

DPO에서 LR을 1e-5로 했을 때:
- Epoch 2에서 Reward Margin이 25+ 로 폭등
- Gradient Norm이 1e-9로 수렴 (거의 학습이 안 됨)
- → "과신(Over-confidence)" 현상: 모든 것을 맞다고 판단

이 때문에 checkpoint-700 (epoch 1.44)에서 멈추고, LR을 5e-6으로 낮추는 방향으로 조정했습니다.

### Q12. CPT와 SFT를 왜 merge(병합)해서 사용하나요? 어댑터 상태로 쓰면 안 되나요?

**답변:**

좋은 질문입니다! LoRA 어댑터는 "원본 모델 위에 얹는 추가 레이어"인데, 이걸 원본에 합치느냐(merge), 따로 두느냐에 따라 동작이 달라집니다.

**Merge하는 이유:**

```
[merge 안 한 경우 - Stacked LoRA]
Base Model (72B) + CPT LoRA + SFT LoRA + DPO LoRA
→ 3개의 LoRA를 동시에 적용해야 함
→ vLLM은 동시에 적용 가능한 LoRA 수가 제한됨 (--max-loras 2)
→ 3개를 동시에 올리면 메모리 부족 + 속도 저하

[merge한 경우 - 우리 방식]
Base Model + CPT LoRA → merge → "CPT+SFT가 녹아든 새 Base"
이 위에 SFT LoRA를 제품별로 올림
→ 어댑터 1개만 올리면 됨!
```

**우리의 실제 구조:**

```
Qwen2.5-72B (원본)
    ↓ CPT LoRA merge
merged_cpt_72b_v10 (CPT가 녹아든 모델)
    ↓ 이 위에 SFT LoRA를 10개 어댑터로 제공
    ├── openframe_base (SFT LoRA)
    ├── openframe_batch (SFT LoRA)
    ├── ...
    └── openframe_gateway (SFT LoRA)
```

**Merge의 장단점:**

| 항목 | Merge | 어댑터 유지 |
|------|-------|-----------|
| 추론 속도 | 빠름 (추가 연산 없음) | 느림 (LoRA 연산 추가) |
| 메모리 | 효율적 | LoRA당 추가 메모리 |
| 되돌리기 | 불가능 | 쉽게 제거 가능 |
| 유연성 | 낮음 | 높음 |

→ CPT는 "항상 적용되어야 하는 기본 지식"이므로 merge가 합리적입니다.
→ SFT는 "제품별로 선택적 적용"이므로 어댑터로 유지합니다.

### Q16. DPO 데이터는 어떻게 만들었나요? Chosen/Rejected 쌍의 생성 방법은?

**답변:**

DPO 데이터는 **"좋은 답변"과 "나쁜 답변"을 쌍으로 만든 것**입니다. 이 쌍을 만드는 4가지 전략이 있습니다:

**전략 1: 제품 교체 (factual_product_swap) - 55.7%**
```
prompt:   "tjesmgr BOOT 명령어를 설명해주세요"
chosen:   "tjesmgr BOOT는 TJES 노드를 초기화합니다." (올바른 TJES 답변)
rejected: "tjesmgr BOOT는 OSC 리전을 시작합니다."     (OSC 답변을 끼워넣음 = 틀림)
```
→ 가장 많이 사용한 전략. 다른 제품의 정보를 rejected로 사용.

**전략 2: 설명 교체 (factual_desc_swap) - 34.4%**
```
prompt:   "에러코드 -5212의 원인은?"
chosen:   "DSALC_ERR_DATASET_NOT_FOUND: 데이터셋을 찾을 수 없습니다"
rejected: "DSALC_ERR_DATASET_LOCKED: 데이터셋이 잠겨 있습니다"  (이름이 틀림)
```
→ 사실 관계(에러 코드, 파라미터 값 등)를 바꿔서 rejected로 사용.

**전략 3: SFT 교차 비교 (sft_cross_match) - 9.4%**
```
prompt:   "HiDB에서 세그먼트 검색 방법은?"
chosen:   (SFT 모델이 잘 답변한 결과)
rejected: (SFT 모델이 틀리게 답변한 결과)
```
→ SFT 학습된 모델의 실제 출력을 비교하여 쌍 생성.

**전략 4: E2E 실패 활용 (e2e_cross_product) - 0.6%**
```
prompt:   (E2E 테스트에서 할루시네이션이 발생한 실제 질문)
chosen:   (정답)
rejected: (할루시네이션이 포함된 실제 응답)
```
→ 실제 시스템 테스트에서 발생한 할루시네이션 사례를 직접 활용.

**DPO 데이터 형식:**

```json
{
  "prompt": "TmaxSoft 제품 전체의 아키텍처를 알려주세요.",
  "chosen": "TmaxSoft는 크게 OpenFrame, JEUS, Tibero, WebtoB로...(정확한 답변)",

## D. LoRA 설정 및 학습 레이어

### Q19. LoRA란 무엇이고, 왜 LoRA를 사용했나요?

**답변:**

LoRA(Low-Rank Adaptation)는 **거대 모델을 효율적으로 학습하는 방법**입니다.

**문제:**
72B 모델을 전체 학습(Full Fine-Tuning)하려면:
```
72B × 4바이트(float32) = 288GB (모델 가중치만)
+ 288GB (Optimizer states)
+ 288GB (Gradients)
= 약 864GB의 GPU 메모리 필요!
→ A100 40GB × 22장 필요 (우리는 4장뿐)
```

**LoRA의 해결 방법:**

LoRA는 원본 모델의 가중치를 **고정(freeze)**하고, **작은 추가 행렬만 학습**합니다.

```
원본 가중치 W (8192 × 8192) → 고정! 절대 건드리지 않음
    +
LoRA A (8192 × 128) × LoRA B (128 × 8192) → 이것만 학습!
```

**비유:**
원본 모델 = 백과사전 (절대 수정 안 함)
LoRA = 포스트잇 (백과사전 위에 추가 메모를 붙이는 것)

**메모리 절약 효과:**

| 방식 | 학습 파라미터 | GPU 메모리 | GPU 필요 수 |
|------|-------------|-----------|-----------|
| Full Fine-Tuning | 73.5B (100%) | ~864GB | 22장 |
| LoRA (r=128) | 842M (1.14%) | ~40GB/장 | 4장 |

→ **학습 파라미터를 99% 줄이면서도 성능은 Full FT의 95%+ 달성**

### Q20. Target Modules로 q,k,v,o,gate,up,down을 선택한 이유는?

**답변:**

이것은 "모델의 어느 부분에 LoRA 포스트잇을 붙일 것인가"에 대한 질문입니다.

**트랜스포머의 각 모듈 역할:**

```
입력 토큰
    ↓
┌─ Self-Attention ──────────────────────────────────┐
│  q_proj (Query):  "이 단어에서 무엇을 찾고 싶은지"    │
│  k_proj (Key):    "이 단어가 가진 정보 키"            │
│  v_proj (Value):  "이 단어가 가진 실제 정보"          │
│  o_proj (Output): "여러 정보를 종합한 결과"           │
└───────────────────────────────────────────────────┘
    ↓
┌─ FFN (Feed-Forward Network) ──────────────────────┐
│  gate_proj: "어떤 정보를 통과시킬지 결정하는 문"       │
│  up_proj:   "정보를 고차원으로 확장"                   │
│  down_proj: "정보를 다시 원래 차원으로 축소"           │
└───────────────────────────────────────────────────┘
    ↓
다음 층으로
```

**왜 7개 모듈 모두를 선택했는가:**

| 선택 범위 | 학습 파라미터 | 효과 |
|----------|-------------|------|
| q,v만 | ~0.3% | 가장 기본적. 논문 원본 권장 |
| q,k,v,o | ~0.6% | Attention만 수정. 지식 주입에 좋음 |
| **q,k,v,o,gate,up,down** | **~1.14%** | **전체 경로 수정. 도메인 특화에 최적** |

우리가 7개 모듈 모두를 선택한 이유:

1. **도메인이 매우 특수함**: OpenFrame은 메인프레임 용어가 많아서, Attention뿐 아니라 FFN(지식 저장소)도 수정해야 함
2. **FFN이 "지식 저장소" 역할**: 연구에 따르면 트랜스포머의 FFN 레이어에 사실적 지식이 저장됩니다. gate/up/down을 학습하면 새로운 도메인 지식을 주입할 수 있음
3. **1.14%면 여전히 효율적**: 7개 모듈을 다 해도 전체의 1%만 학습하므로 충분히 효율적

**비유:**
- q,v만 학습 = "눈(보는 방식)만 교정"
- q,k,v,o 학습 = "눈 + 귀(듣는 방식)까지 교정"
- **전체 7개 학습 = "눈 + 귀 + 뇌의 판단 방식까지 교정"**

### Q21. LoRA Rank를 CPT=64, SFT=128, DPO=32로 다르게 설정한 이유는?

**답변:**

LoRA Rank(r)는 **"포스트잇의 크기"**와 같습니다. Rank가 높을수록 더 많은 정보를 학습할 수 있지만, 메모리도 더 많이 사용합니다.

**각 단계별 Rank 설정 이유:**

```
CPT (r=64):   "교과서 읽기" → 도메인 지식은 중간 크기면 충분
SFT (r=128):  "Q&A 패턴 학습" → 22개 제품의 다양한 Q&A 패턴을 저장하려면 큰 Rank 필요
DPO (r=32):   "미세 조정" → 선호도만 살짝 조정하면 되므로 작은 Rank로 충분
```

**기술적 설명:**

LoRA에서 Rank는 추가되는 행렬의 "내부 차원"입니다:

```
원본: W (8192 × 8192) = 67,108,864 파라미터
LoRA r=32:  A(8192×32) × B(32×8192) = 524,288 파라미터 (원본의 0.78%)
LoRA r=64:  A(8192×64) × B(64×8192) = 1,048,576 파라미터 (원본의 1.56%)
LoRA r=128: A(8192×128) × B(128×8192) = 2,097,152 파라미터 (원본의 3.13%)
```

**왜 SFT가 가장 큰 Rank인가:**

| 이유 | 설명 |
|------|------|
| 제품 다양성 | 22개 제품의 각기 다른 Q&A 패턴을 하나의 어댑터에 저장해야 함 |
| 형식 복잡성 | 시스템 프롬프트 + 질문 + 구조화된 답변 + 출처 표기 등 복잡한 형식 |
| 다국어 | 한/일/영 3개 언어의 응답 패턴을 모두 학습 |

**왜 DPO가 가장 작은 Rank인가:**

| 이유 | 설명 |
|------|------|
| 목적이 단순 | "좋은 답 vs 나쁜 답"의 차이만 학습하면 됨 |
| 과적합 위험 | Rank가 크면 학습 데이터를 외워버릴 수 있음 (356쌍뿐) |
| 기존 지식 보존 | 작은 Rank로 기존에 잘 학습된 모델을 최소한으로 수정 |

### Q22. LoRA Alpha는 왜 Rank의 2배로 설정했나요?

**답변:**

LoRA Alpha(α)는 **LoRA의 학습 결과를 원본 모델에 얼마나 세게 반영할지**를 결정하는 "볼륨 노브"입니다.

**공식:**
```
실제 반영 강도 = α / r × LoRA 출력

예:
r=64, α=128 → 반영 강도 = 128/64 = 2.0배
r=64, α=64  → 반영 강도 = 64/64 = 1.0배
r=64, α=32  → 반영 강도 = 32/64 = 0.5배
```

**우리의 설정:**

| 단계 | Rank (r) | Alpha (α) | α/r 비율 | 이유 |
|------|----------|----------|---------|------|
| CPT | 64 | 128 | 2.0 | 도메인 지식을 강하게 반영 |
| SFT | 128 | 256 | 2.0 | Q&A 패턴을 강하게 반영 |
| DPO | 32 | 64 | 2.0 | 선호도를 적절히 반영 |

**α/r = 2.0을 사용한 이유:**

1. **α/r = 1.0** (Rank와 같음): LoRA 논문의 원래 권장값. 보수적인 학습에 적합
2. **α/r = 2.0** (우리의 선택): 학습 효과를 2배로 증폭. 도메인이 매우 특수하므로 강한 적응이 필요
3. **α/r > 2.0**: 불안정해질 수 있음. 학습이 발산할 위험

비유하면:
- α/r = 1.0: "새로 배운 것을 조심스럽게 적용"
- α/r = 2.0: "새로 배운 것을 자신감 있게 적용"
- α/r = 4.0: "새로 배운 것만 믿고 기존 것은 무시" → 위험!

### Q23. 왜 80개 레이어 중 전체에 LoRA를 적용했나요? 일부만 학습하면 안 되나요?

Qwen2.5-72B는 80개의 트랜스포머 레이어로 구성되어 있습니다. 우리는 **80개 레이어 모두에 LoRA를 적용**했습니다.

**레이어별 역할 (연구 결과에 기반):**

```
레이어 1~20 (하위층):   토큰의 기본 문법, 형태소 처리

**CPT에서 추가로 학습하는 특수 레이어:**

### Q24. 학습 시 Gradient Checkpointing을 사용한 이유는?

**답변:**

Gradient Checkpointing은 **GPU 메모리를 절약하기 위한 기술**입니다. 대신 학습 속도가 약간 느려집니다.

**문제: Activation 메모리**

딥러닝에서 역전파(Backpropagation)를 하려면, 순전파(Forward) 때 각 층의 중간 결과(Activation)를 저장해야 합니다:

```
[일반 방식]
Layer 1 → 결과 저장 → Layer 2 → 결과 저장 → ... → Layer 80 → 결과 저장
                                                              ↓
                                               역전파: 저장된 결과를 역순으로 사용

메모리: 80개 레이어의 결과를 모두 저장 = 엄청난 메모리!
```

```
[Gradient Checkpointing]
Layer 1 → 결과 저장 → Layer 2 → 버림 → Layer 3 → 버림 → ... → Layer 20 → 결과 저장
                                                                         ↓
                                               역전파: Layer 1~20 사이는 다시 계산!

메모리: 일부만 저장 = 메모리 대폭 절약!
속도: 역전파 시 재계산 필요 = 약 30% 느려짐
```

**비유:**
- 일반 방식 = 수학 풀이를 전부 메모지에 적어놓고 나중에 검산
- Gradient Checkpointing = 핵심 중간값만 메모하고, 나머지는 검산할 때 다시 계산

**우리 시스템에서의 효과:**

| 항목 | Checkpointing OFF | Checkpointing ON |
|------|-------------------|------------------|
| Activation 메모리 | ~15GB/GPU | ~3GB/GPU |
| 학습 속도 | 1.0x | ~0.7x (30% 느림) |
| 72B 학습 가능? | 불가 (OOM) | 가능 |

→ A100 40GB에서 72B 모델을 학습하려면 **Gradient Checkpointing은 필수**입니다.

## E. 양자화 및 추론 서빙

### Q25. 4-bit NF4 양자화란 무엇이고, 왜 사용했나요?

**답변:**

양자화(Quantization)는 **모델의 숫자 정밀도를 낮춰서 메모리를 절약**하는 기술입니다.

**숫자 표현 방식:**

```
float32 (32비트): 1.23456789... → 매우 정밀, 4바이트/숫자
float16 (16비트): 1.2346...     → 정밀, 2바이트/숫자
int8    (8비트):  1.23          → 보통, 1바이트/숫자
int4    (4비트):  1.2           → 낮음, 0.5바이트/숫자
```

**NF4 (Normal Float 4-bit)는 무엇인가:**

일반 4비트 양자화는 숫자를 균등하게 분포시키지만, NF4는 **정규분포(Normal Distribution)에 맞게 분포**시킵니다. 왜냐하면 모델의 가중치가 대부분 0 근처에 몰려있기 때문입니다.

```
[일반 4비트]
-8, -6, -4, -2, 0, 2, 4, 6  → 균등 분포

[NF4]
-1.8, -0.9, -0.4, -0.15, 0, 0.15, 0.4, 0.9, 1.8  → 0 근처에 촘촘
```

→ NF4는 0 근처의 값을 더 정밀하게 표현해서, **같은 4비트인데 정보 손실이 적습니다**.

**Double Quantization까지 사용:**

우리는 `bnb_4bit_use_double_quant=True`로 설정했습니다. 이것은 "양자화의 양자화"입니다:
```
1차 양자화: 가중치 → 4비트 (+ 양자화 상수 저장)
2차 양자화: 양자화 상수도 → 8비트로 압축!
```
→ 추가로 약 0.4GB의 메모리를 절약합니다.

**메모리 절약 효과:**

| 정밀도 | 72B 모델 크기 | A100 GPU 수 |
|--------|-------------|------------|
| float32 | 288GB | 8장 |
| float16 | 144GB | 4장 |
| int8 | 72GB | 2장 |
| **NF4 (4bit)** | **~36GB** | **1장 (하지만 TP=4로 분산)** |

→ 4비트 양자화 덕분에 72B 모델을 **GPU 4장으로 학습 + 추론** 모두 가능합니다.

### Q26. vLLM에서 --enforce-eager 옵션을 사용한 이유는?

**답변:**

`--enforce-eager`는 **CUDA Graph 최적화를 끄는** 옵션입니다. 성능이 약간 떨어지지만, 안정성을 위해 사용합니다.

**CUDA Graph란:**

```
[일반 모드 (Eager)]
Python → CUDA 커널 1 호출 → 완료 → CUDA 커널 2 호출 → 완료 → ...
         ↑ 매번 CPU-GPU 통신 오버헤드 발생

[CUDA Graph 모드]
1회차: Python → 커널 1 → 커널 2 → ... (실행 순서를 기록)
2회차~: 기록된 순서를 GPU에서 한 번에 실행! (CPU 개입 없음)
         ↑ 오버헤드 제거, 약 10~30% 빠름
```

**그런데 왜 끄나요?**

| 이유 | 설명 |
|------|------|
| LoRA 동적 스위칭 | 요청마다 다른 LoRA 어댑터를 사용하는데, CUDA Graph는 고정된 연산만 지원 |
| BitsAndBytes 양자화 | 4비트 양자화와 CUDA Graph가 호환되지 않는 경우가 있음 |
| 메모리 안정성 | CUDA Graph는 추가 메모리를 사용하는데, 이미 90% 사용 중 |

**성능 영향:**

| 모드 | 처리량 | 안정성 |
|------|--------|--------|
| CUDA Graph ON | ~8 tok/s | LoRA 스위칭 시 크래시 가능 |
| **Eager (현재)** | **~6 tok/s** | **안정적** |

→ 약 25%의 성능을 포기하고 **안정성을 선택**했습니다.

### Q27. --max-loras 2는 동시에 2개의 LoRA만 사용할 수 있다는 뜻인가요?

**답변:**

네, 정확합니다! 하지만 "동시에"의 의미를 정확히 이해해야 합니다.

**구조:**

```
vLLM 서버
├── GPU 메모리에 상주하는 LoRA: 최대 2개 (--max-loras 2)
├── CPU 메모리에 대기하는 LoRA: 최대 24개 (--max-cpu-loras 24)
└── 등록된 전체 LoRA: 10개 (SFT 어댑터)
```

**동작 방식:**

```
요청 A: model="openframe_base" → GPU에 openframe_base 로드 (GPU 슬롯 1/2)
요청 B: model="openframe_osc"  → GPU에 openframe_osc 로드 (GPU 슬롯 2/2)
요청 C: model="openframe_hidb" → GPU 슬롯이 가득!
                                 → 가장 오래된 LoRA를 CPU로 내림
                                 → openframe_hidb를 GPU로 올림
                                 → 약간의 지연 발생
```

**비유:**
- GPU = 책상 (2권만 올려놓을 수 있음)
- CPU = 책장 (24권 보관 가능)
- 새 책이 필요하면 책상 위의 책을 책장에 넣고 새 책을 올림

**왜 2로 설정했나요?**

| max-loras | GPU 메모리 추가 사용 | 장점 | 단점 |
|-----------|-------------------|------|------|
| 1 | 최소 | 메모리 절약 | 어댑터 교체 빈번 |
| **2** | **약 1GB 추가** | **2개 동시 처리** | **적당한 메모리** |
| 4 | 약 2GB 추가 | 교체 빈도 낮음 | 메모리 부족 위험 |

→ A100 40GB에서 72B 모델 + KV Cache + LoRA 2개가 **최적의 균형**입니다.

### Q28. GPU Memory Utilization 0.90의 의미와 나머지 10%는?

**답변:**

`--gpu-memory-utilization 0.90`은 **각 GPU의 40GB 중 90%인 36GB를 vLLM이 사용**한다는 뜻입니다.

**메모리 사용 내역:**

```
A100 40GB 한 장의 메모리 분배:

┌─────────────────────────────────────────────┐
│ 모델 가중치 (4bit NF4)       ~9.5GB (1/4)  │ ← 72B/4=18B, 4bit=~9.5GB
│ LoRA 어댑터 (GPU 슬롯 2개)   ~0.5GB        │ ← 활성 LoRA 2개
│ KV Cache                     ~20GB         │ ← 가장 큰 부분! 사용자 대화 저장
│ CUDA 커널/워크스페이스         ~3GB          │ ← GPU 연산용 임시 공간
│ vLLM 내부 버퍼               ~3GB          │ ← 토큰 처리 버퍼
├─────────────────────────────────────────────┤
│ 예약됨 (사용 안 함)           ~4GB (10%)   │ ← 안전 마진
└─────────────────────────────────────────────┘
총: 40GB
```

**10% 예약의 이유:**

| 이유 | 설명 |
|------|------|
| CUDA 메모리 단편화 | GPU 메모리가 100% 차면 조각화 현상 발생 |
| 돌발 메모리 수요 | 긴 입력이나 여러 LoRA 동시 교체 시 일시적 메모리 급증 |
| 시스템 안정성 | OOM(Out of Memory) 에러로 서버 크래시 방지 |
| GPU 드라이버 | NVIDIA 드라이버 자체가 약 500MB 사용 |

**KV Cache가 가장 큰 이유:**

KV Cache는 각 사용자의 대화 맥락을 저장하는 공간입니다:
```
동시 사용자 1명: 4096 토큰 × 80층 × 2(K+V) × 1024바이트 ≈ 640MB
동시 사용자 63명: 640MB × 63 ≈ 39GB... → 4장에 분산 = ~10GB/장
실제: ~20GB (여유 포함)
```
